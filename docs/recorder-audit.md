# Recorder review

The FFmpeg recorder is enabled only in configurations with the required bundled FFmpeg libraries; other builds use the no-FFmpeg stubs. The reported symptoms have not been reproduced on a real machine in this environment.

## Changes and numbered findings

1. When recording and replay are both active, capture now performs one framebuffer read and copies it once for the second queue. Each queue still owns and frees its own pixels; timestamps are shared. Full queues and allocation failures drop frames. Actual GPU performance has not been measured.
2. Failure to create the replay audio stream now disables audio muxing without dereferencing the missing stream. Recording already had a guard, but previously overwrote the packet count and leaked the allocated audio packets on that path; the mux count is now separate from the ownership count in both paths.
3. The running flags read by audio are now changed and checked under the corresponding PCM mutex, with the buffer pointer checked under that same lock. The audio-thread run flag has its own mutex. This prevents a stale decision to write after a pipeline's buffer has been freed while the other pipeline remains active. The encode queue's running flag and queue count are checked under the queue mutex rather than relying on `volatile`. No C11 atomics or toolchain standard change is required.
4, 5, 9, 16. The two save paths use a shared bounded audio encoder helper that checks array allocation, packet allocation, packet capacity, frame writability, resampler setup/conversion and encoder submission. Video packet drains also check packet allocation. An allocation or encoder failure can result in partial or silent output, with logging, rather than a crash. The fixed bound is still twice the input audio frame count; packets beyond it are dropped, not dynamically grown.
6. Both pipelines now stop on a drawable-size change, on the main thread, with an on-screen warning. Recording is finalized; replay stop **clears its buffered replay**, so save a replay before resizing. A minimized zero-sized drawable waits until dimensions are valid. Workers use the pipeline's original dimensions rather than concurrently reading mutable settings. This avoids encoding a queued old-sized image with new dimensions; automatic segmentation/restart was not implemented.
7. Recording snapshot allocation and packet-clone failures now release packet buffers, PCM and encoder resources after joining the worker. Clone failure had an additional unchecked NULL path. Cleanup also covers packet-array allocation failure during start.
8, 11, 13. Recording and replay encode-thread startup failures now release their owned resources; replay also stops and joins the shared audio thread when recording does not need it. Earlier buffer initialization failures free the codec-parameter snapshot as well. Failure paths have been inspected but not exercised with real FFmpeg/thread-creation failures.
10. Kept the audio stop boundary at the user's stop request, before draining the existing video queue: draining processes frames captured *before* that request, it does not capture new video. Continuing to capture audio during an arbitrarily slow drain would append audio after the requested endpoint, not synchronize timestamps. Exact synchronization is still limited: audio is collected in chunks without per-chunk timestamps, and both streams are normalized separately when saved.
12, 21. Replay codec parameters and time base are snapshotted after opening the encoder and before the worker starts. Save no longer reads the live codec context and refuses inactive buffers (stop clears them). The recording context is read only after joining its worker. Save also rescales AAC packet timestamps from the encoder time base to the muxer's possibly changed stream time base.
14. PCM snapshot copying remains under the mutex and can stall capture; avoiding that safely requires a different ownership/ring design and profiling. PulseAudio reads and thread joins may themselves block; these changes do not make shutdown bounded.
15, 18, 20, 22. As the review already qualifies, the dimension log is accurate, and `free(NULL)` is valid. `file_dir_create` already treats an existing directory as success, and `chat_add` is declared by the included `common.h`. No changes were necessary for these claims.
17. The fallback duration of 1024 for AAC packets that report zero remains. Its interaction with encoder delay, final partial frames and MP4 gapless metadata requires actual FFmpeg playback tests; partial input samples are still not encoded.
19. Pulse monitor detection still uses synchronous `popen` at initialization; startup delays depend on the environment. Moving it off the main thread needs a separate device selection/lifecycle design.

Additional fixes: the replay video ring cleanup previously freed the same oldest slot repeatedly, leaking other packets, and overwriting a full ring did not subtract the displaced duration. The PCM ring's byte count now clamps at capacity even when its size is not a multiple of the audio chunk, and recording PCM capacity is consistently measured in frames; failed `realloc` no longer loses the old allocation.

## Verification and limits

All 91 Python scripts passed. Extracted C tests exercise a single read for both queues, independent queue ownership and full queues, resize stop, AAC packet limits/allocation failure, conversion failure, and a PulseAudio-read/PCM-free overlap while recording continues. The FFmpeg-enabled code was syntax-checked using configured FFmpeg 7.1.2 headers and PulseAudio 17 headers, with stub GL; the no-FFmpeg branch was also syntax-checked. These are not linked production builds. No real encoder, PulseAudio server, GPU, MP4 playback, simultaneous F7/F8 session, resize interaction, or OOM/thread-failure injection against the complete application was available. Existing synchronous muxing, error reporting, frame drops, audio/video synchronization and potentially unbounded PulseAudio blocking need live testing.

## Follow-up: recording audio ending early

Audio and video were previously each normalized to their own first packet, so a slow audio-device open could shift the recorded audio earlier by the entire startup delay and make it end early. The recorder now estimates the first PCM block's start from the read-completion clock minus one 1024-sample block, clamps it to the recording start, and applies the positive difference from the first video packet to both audio interleaving and MP4 timestamps. This is an estimate: `pa_simple_read` does not provide sample timestamps, server/device buffering is not measured, early audio relative to the first video frame is clamped rather than trimmed, and later stalls or clock drift are not corrected. Replay timestamp alignment is unchanged.

PulseAudio open and read failures are logged and reported via a mutex-protected event delivered on the main/game thread; background threads do not call `chat_add`. The thread-running flag retains its existing meaning of **joinable thread**, even after a worker exits, so the owner can still join it. A separate dead flag informs newly started pipelines when the shared capture worker has failed. To retry capture after such a failure, stop both recording and replay, then start again. Automatic reconnect is deliberately not implemented: concatenating samples across a lost interval without timestamping or inserting silence would hide the gap and shift all later audio.

The earlier PCM realloc leak had already been fixed in the main review. A failed growth now additionally logs and reports the truncation once, keeps the original buffer, and stops appending to that recording to avoid silently closing a gap if a later allocation succeeds. Video continues. Audio capture is still stopped at the stop request rather than after video queue drain: queued frames carry timestamps from before the request, and drain duration is not additional captured-video duration. A read in flight at stop can still be discarded, so short tail loss remains possible; this does not explainably imply that the last 8 video frames occurred after the stop request.

The recorder logs estimated PCM start offset and captured audio duration. Compare those values with the recording's video duration and look for `audio capture read failed` or `PCM allocation failed` when investigating a real cutoff. Save/encode failures, underruns, PulseAudio stalls, device buffering, wall-clock changes and playback behavior remain possible causes; this review cannot identify which occurred without a sample/log and live reproduction.

Follow-up tests: extracted worker tests cover read failure, memory-growth failure, preserved PCM and first-chunk timestamp; the optional `RECORDER_FFMPEG_DIR` test uses real FFmpeg 7.1.2 AAC encoding and MP4 muxing and verified a synthetic three-second start offset (`ffprobe`: 3.000000 s start, 2.026667 s duration). All 92 Python scripts pass (the real-FFmpeg test is skipped unless configured). FFmpeg/Pulse headers plus stub GL were used for syntax checks; no real PulseAudio capture or full game recording was available.
